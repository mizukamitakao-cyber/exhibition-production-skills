# 04 Museum Onboarding 設計

文書日：2026年11月18日  
文書区分：Phase 1 Onboarding設計  
ステータス：Phase 1確定

---

## 1. 概要

Museum Onboardingは、館の担当者との対話を通じて **館別プロファイル（museum-profile.yaml）** を作成するプロセスである。

**設計原則：**
- 1回のやり取りで提示する質問は1〜3問とする
- 確認済みの情報を重複して質問しない
- 提供資料から確認できる情報はヒアリングで確認しない
- AIの提案を正式設定として自動登録しない
- 未設定・不明な項目は `unset` として扱い、推測で埋めない
- セッションはいつでも中断・再開できる

---

## 2. 状態遷移

```
         ┌─────────────────────────────────────────────┐
         ↓                                             │
  [not_started]                                        │
         │ /exhibition-museum-onboarding 実行           │
         ↓                                             │
  [in_progress] ←──────── 再開 ──────────── [paused]  │
         │                                             │
         │ 全フェーズ完了                               │
         ↓                                             │
  [ready_for_review]                                   │
         │ 担当者確認・承認                             │
         ↓                                             │
     [approved] ──── 改訂指示 ──── [revision_in_progress]
```

**状態の説明：**

| 状態 | 意味 |
|------|------|
| `not_started` | セッション未開始（初期状態） |
| `in_progress` | ヒアリング中 |
| `paused` | 中断（`onboarding-session.yaml`に進捗保存済み） |
| `ready_for_review` | ヒアリング完了・担当者確認待ち |
| `approved` | プロファイルが担当者に承認された |
| `revision_in_progress` | 承認後に改訂中 |

## 3. ヒアリングフェーズとキュー

ヒアリングは8フェーズに分かれる。各フェーズの質問を順番に消化し、フェーズ完了後に次フェーズへ進む。

### 3.0 質問定義の外部化

ヒアリング質問はスキルのコードに直書きせず、以下の外部ファイルに定義する。

```
core/skills/exhibition-museum-onboarding/references/questions.yaml
```

**外部化の目的：**
- 専門分野の追加や質問内容の見直しをスキル改修なしに行える
- 質問の表現・順序・必須区分を設定ファイルとして管理できる

**questions.yaml の構造：**
```yaml
version: "1.0"
phases:
  - phase_id: "basic"
    questions:
      - id: "B-01"
        text: "館の正式名称を教えてください"
        field: "basic.name"
        required: true
      - id: "B-02"
        text: "施設の種別はどれですか（博物館・資料館・文化施設・その他）"
        field: "basic.type"
        required: true
      # ...
  - phase_id: "visitors"
    questions:
      # ...
domain_questions:              # 専門分野別の追加質問
  history:
    - id: "DH-01"
      text: "年代の表記方式を教えてください（西暦・和暦・並記）"
      field: "writing.notation_rules"
      required: false
  # 新しい分野はここに追加するだけで対応可能
```

本設計文書§3.2に記載の質問内容は `questions.yaml` の初期値として実装される。

## 4. 専門分野別の質問分岐

`basic.domains` の値に応じて、追加質問を提示する。

| 専門分野 | 追加質問 |
|---------|---------|
| `history` | 年代の表記方式（西暦・和暦・並記）、特定の歴史観に関する方針 |
| `art` | 作品保護に関する表現制限、来歴・権利の確認基準 |
| `natural_history` | 学名・和名の表記方針、絶滅危惧種等の表現ガイドライン |
| `science` | 技術的正確性の基準、非専門家向け解説のレベル感 |

## 5. 資料からの情報抽出

担当者が資料（PDF・Word・テキスト等）を提供した場合：

1. 資料を読み込み、ヒアリング質問に対応する情報を抽出する
2. 抽出した情報を `profile-evidence.yaml` に `status: "documented"` として記録する
3. 資料から確認できた質問は、担当者に「〇〇に記載の内容で合っていますか？」と確認するだけでよい。担当者が確認した場合、その質問を `answered_questions` に `source: "document"` として追加し、次のヒアリングでの質問キューから除外する
4. 担当者が確認しなかった（不明・保留）場合は `status: "documented"` のまま保持し、後で再確認キューに入れる
5. 資料と担当者回答の間に矛盾がある場合は `status: "conflict"` として記録し、担当者に確認を求める

---

## 6. 矛盾検出ルール

以下のケースを矛盾として検出し、`onboarding-session.conflicts` に記録する：

| 矛盾のパターン | 対応 |
|-------------|------|
| 資料と回答で異なる値 | `conflict` として記録し、どちらが正しいか確認を求める |
| 論理的に相反する値（例：パネル文字数0 & 長文方針） | 確認質問を生成する |
| 必須フィールドへの「不明」回答 | `unset` として記録し、後で再確認のキューに入れる |

**矛盾の解消方法：**  
担当者が正しい値を回答した時点で `conflict` を解消し、採用した値と根拠を記録する。

---

## 7. 中断・再開

**中断（pause）：**  
- ユーザーが「中断」「後で続ける」と指示したとき
- セッションが長時間（目安：1時間）応答なしのとき
- 保存先への書き込みエラーが発生したとき

中断時の処理：
1. `onboarding-session.yaml` を `status: "paused"` で保存する
2. `paused_at`・`paused_reason` を記録する
3. 再開時に必要な情報（現在フェーズ、未回答質問）を提示する

**再開：**  
1. `onboarding-session.yaml` を読み込む
2. `answered_questions` を確認し、済みの質問をスキップする
3. `pending_questions` から次の質問を提示する
4. 長期中断の場合（目安：1週間以上）、主要な回答内容を要約して確認を促す

## 8. 承認フロー

ヒアリング完了後、プロファイルの承認は以下の手順で行う：

```
1. Museum Onboardingが museum-profile-draft.yaml を生成する
2. ステータスを ready_for_review に変更する
3. 担当者にプロファイルの内容を提示する（全項目一覧形式）
4. 担当者が確認・修正指示を出す
   ├── 修正あり：指摘箇所を更新し、ステータスをin_progressに戻す
   └── 承認：
         museum-profile-v{N}.yaml として確定保存する
         ステータスを approved に変更する
         approval-record を作成する
         draft ファイルを _backup/ に移動する
```

**承認済みプロファイルの保護：**  
- `museum-profile-v{N}.yaml`（承認済み）はファイル属性で読み取り専用に設定する
- 更新する場合は `revision_in_progress` 状態で新しいドラフトを作成し、承認後に `v{N+1}` として保存する

---

## 9. 館別プロファイルの生成規則

セッションのヒアリング結果から `museum-profile.yaml` を生成する際のルール：

- 回答済みフィールドのみ設定値として記録する
- `unset` のフィールドは空値（`null`または`[]`）のまま残す
- AIが提案した値には必ず `status: "proposed"` を付与し、担当者確認前に `confirmed` にしない
- 設定値には必ず対応する `profile-evidence` エントリを作成する

---

## 10. 設定変更時の影響管理

承認済みプロファイルの改訂後、Exhibition Directorは以下を確認する：

| 変更されたフィールド | 影響する成果物 | 対応 |
|----------------|-------------|------|
| `writing.*` | 承認済み原稿 | 再レビューが必要な原稿リストを生成 |
| `exhibition_policy.content_restrictions` | 全成果物 | Reviewerによる適合確認を推奨 |
| `research.*` | 出典台帳・調査メモ | 未確認情報の再調査が必要な可能性を通知 |
| `operations.approval_flow` | 進行中の承認状態 | 新フローの適用タイミングを担当者に確認 |

変更が進行中案件に影響する場合は、担当者に影響範囲を提示して判断を求める。  
変更後の版を使用していない既存承認済み成果物は自動的に再承認しない。

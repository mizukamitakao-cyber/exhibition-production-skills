# 企画展示制作AI Skills
## Phase 1 詳細設計・Claude Code開発指示書

Version 1.0｜2026年11月17日  
基準文書：企画展示制作AI Skills 基本構想 v0.3

## 1. Phase 1の目的

Phase 1では、企画展示制作AI Skillsの共通基盤を設計する。初期開発はClaude Codeで行い、将来のCodex対応を想定する。

**Phase 1の目的はSkillsの実装開始ではなく、後続開発の手戻りを防ぐための技術仕様と安全なデータ管理方式の確定である。**

### 対象

| 対象 | 設計内容 |
|---|---|
| 開発環境 | Claude Code、Python、Git等の利用環境 |
| システム構成 | 共通コア、環境別アダプター、館別データの分離 |
| Skills構造 | 役割、入出力、呼び出し方法 |
| 館別プロファイル | データスキーマ、設定の継承・更新 |
| Museum Onboarding | ヒアリング、状態管理、承認方式 |
| 案件管理 | 新規制作・既存改訂の共通データ構造 |
| データ保護 | 保存先、原本保護、履歴、復旧 |
| 品質管理 | Advocate・Reviewerとの連携仕様 |
| テスト | 検証方法、受入基準 |

### 対象外

- Skillsの本格実装
- 実際の企画展示制作
- 実資料を使ったAI調査
- Claude Code・Codexの同時開発
- 外部サービス・データベース接続
- 実在館の非公開資料の読み込み
- 本番データの変更・削除

## 2. Phase 1の実施方式

1. **Step 1-1：開発環境の現状調査** — 作業ディレクトリ、Git、Python、権限等を確認。
2. **Step 1-2：アーキテクチャ詳細設計** — 共通コア、環境別アダプター、Skills責務を定義。
3. **Step 1-3：データ・安全性・Onboarding詳細設計** — プロファイル、ヒアリング、承認、版管理、保存・復旧を定義。
4. **Step 1-4：レビュー・実装計画確定** — 設計整合性を検証し、Phase 2以降の実装タスクを整理。

各Stepの成果物を確認して次へ進む。現段階では設計文書作成までを許可し、プログラム実装は許可しない。ただし初回実行ではファイル作成も行わず、調査・設計方針をチャットで報告する。

## 3. アーキテクチャ詳細設計の要件

### 3.1 共通コアと実行環境の分離

```text
exhibition-production-skills/
├── core/
│   ├── skills/
│   ├── workflows/
│   └── policies/
├── adapters/
│   ├── claude-code/
│   └── codex/
├── schemas/
├── templates/
├── scripts/
├── tests/
└── docs/
```

これは確定構成ではない。Claude CodeとCodexのSkill検出・配置・実行仕様を確認し、共通ファイルの重複管理を避ける方式を比較する。

確認対象：Skill定義形式と配置、プロジェクト指示ファイル、Skill間連携、Pythonスクリプト呼び出し、外部ファイルアクセス制限、Windowsパス・権限。

### 3.2 Skillsの責務

| 機能 | 主な責務 |
|---|---|
| Deployment Setup | 導入環境の確認・設定 |
| Museum Onboarding | 館別設定のヒアリング・管理 |
| Exhibition Director | 制作工程の統括 |
| Idea Generator | 企画アイディア創出 |
| Researcher | 調査・出典管理 |
| Planner | 企画書作成 |
| Story Designer | 展示構成設計 |
| Exhibition Writer | 原稿制作・改訂 |
| Visual Designer | デザイン・レイアウト案 |
| Advocate | 批判的検討・改善提案 |
| Reviewer | 品質・要件適合性の検証 |

各機能の入力、出力、依存設定、実行条件、承認条件、失敗時の動作を定義する。11個の独立エージェント実装は前提としない。

## 4. データモデルの詳細設計

### 4.1 共通データの分類

| データ | 主な内容 |
|---|---|
| museum-profile | 館別設定 |
| profile-evidence | 設定値の根拠・確認状態 |
| onboarding-session | ヒアリングの進捗 |
| exhibition-project | 展示案件 |
| artifact-manifest | 成果物一覧と版 |
| source-registry | 調査資料と出典 |
| review-record | Advocate・Reviewerの指摘 |
| approval-record | 承認・差し戻し |
| operation-record | 保存・変更等の操作記録 |

各モデルのID、スキーマ版、作成・更新情報、参照関係、検証条件を定義する。

### 4.2 館別プロファイル

共通設定→専門分野別設定→館別設定→案件別設定の4階層を設ける。設定の型、必須項目、初期値、未設定値、継承・上書き、上書き禁止安全ルール、根拠・確認状況、承認・版管理、スキーマ移行方針を確定する。

人間編集形式はYAML、機械検証はJSON Schemaを想定し、実際のライブラリ選定は調査後に決定する。

### 4.3 Museum Onboardingのヒアリング制御

| 状態 | 意味 |
|---|---|
| `not_started` | 未開始 |
| `in_progress` | ヒアリング中 |
| `paused` | 中断 |
| `ready_for_review` | 確認待ち |
| `approved` | 承認済み |
| `revision_in_progress` | 改訂中 |

質問選択・分岐、回答保存、提供資料との照合、矛盾検出、再質問、承認済み設定の改訂を設計する。原則一度に1〜3問とし、確認済み情報を重複質問しない。

### 4.4 データ保存・安全性

ローカルファイルを正本とし、許可領域、原本・作業データ分離、パストラバーサル・シンボリックリンク等による領域逸脱防止、書き込み障害、競合更新、バックアップ・復旧、監査記録、承認済み成果物保護を設計する。Windows優先としつつ他OS移植を妨げない。
